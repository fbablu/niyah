# Lane B migration: custom plugins → @bacons/apple-targets

Date: 2026-05-16. Reason: custom plugins kept hitting empty-Sources-phase + addSourceFile bugs whenever Xcode held the project. apple-targets uses Xcode 16 `PBXFileSystemSynchronizedRootGroup`, which auto-includes every file in `targets/<name>/` — eliminates the whole bug class.

## What changed

- **Added**: `@bacons/apple-targets@4.0.7` (patched via `pnpm patch` to add `device-activity-report` to the registry — upstream PR pending).
- **Added**: `targets/` directory at project root with 5 subdirs:
  - `widget/` → Live Activity (bundle `com.niyah.app.live-activity`, iOS 16.1)
  - `monitor/` → DeviceActivityMonitor (bundle `com.niyah.app.device-activity-monitor`, iOS 16.0)
  - `report/` → DeviceActivityReport (bundle `com.niyah.app.device-activity-report`, iOS 16.0)
  - `shieldaction/` → ShieldActionDelegate (bundle `com.niyah.app.shield-action`, iOS 16.0)
  - `shieldconfig/` → ShieldConfigurationDataSource (bundle `com.niyah.app.shield-config`, iOS 16.0)
- **Each target**: `expo-target.config.json` (type + bundleId + deploymentTarget + entitlements + frameworks) + ported Swift sources.
- **Removed** plugins: `withDeviceActivityMonitor.js`, `withShieldExtensions.js`, `withDeviceActivityReport.js`, `withLiveActivity.js`, `withScreenTimeEntitlement.js`.
- **app.config.js**: entitlements (`com.apple.developer.family-controls`, `application-groups`, `aps-environment`) moved into `ios.entitlements`. `NSSupportsLiveActivities` + `NSFamilyControlsUsageDescription` moved into `ios.infoPlist`. Added `ios.appleTeamId: "4R55F73KCP"`. Added `@bacons/apple-targets` at end of plugins array. Lane B is no longer gated by env var — extensions always register.
- **Renamed Swift classes** (must match apple-targets' default NSExtensionPrincipalClass):
  - `NiyahDeviceActivityMonitorExtension` → `DeviceActivityMonitorExtension`
  - `NiyahShieldActionExtension` → `ShieldActionExtension`
  - `NiyahShieldConfigurationDataSource` → `ShieldConfigurationExtension`
  - Widget bundle + report extension keep `Niyah*` prefix (use `@main`, no plist class binding).
- **Removed**: 5 Swift subdirs at `modules/niyah-screentime/ios/Niyah*/` (now in `targets/`). Kept top-level: `NiyahScreenTimeModule.swift`, `NiyahActivityAttributes.swift`, `AppPickerHostingController.swift`.
- **Bumped**: `@sentry/react-native` 6.15.1 → 6.22.0 (kills the HermesRuntime API patch we used to make in `node_modules`).
- **Kept**: `withFollyCoroutinesFix.js` + `withFmtConstevalFix.js` (still required on RN 0.81 + Xcode 26 until SDK 56).

## Patch persistence

`patches/@bacons__apple-targets@4.0.7.patch` — adds `device-activity-report` to the registry. Survives `pnpm install` via the `patchedDependencies` block pnpm auto-wrote in `package.json`. Verify it's committed.

## Manual steps for Fardeen

### Before first build

1. **Verify Apple Developer portal** has these 5 App IDs registered with capabilities:
   - `com.niyah.app.device-activity-monitor` — Family Controls (Development + Distribution), App Groups
   - `com.niyah.app.device-activity-report` — Family Controls (Development + Distribution **— form may need re-submitting**), App Groups
   - `com.niyah.app.live-activity` — App Groups
   - `com.niyah.app.shield-action` — Family Controls, App Groups
   - `com.niyah.app.shield-config` — Family Controls, App Groups
2. **App Group**: `group.com.niyah.app` exists and is enabled on all 6 bundle IDs (main app + 5 extensions).
3. **FamilyControls Distribution form** at https://developer.apple.com/contact/request/family-controls-distribution — submit if not already approved for `com.niyah.app.device-activity-report`. (Other 4 already approved per memory.)

### Build

```bash
# Local USB device build:
pnpm build:local

# OR open Xcode and run:
open ios/Niyah.xcworkspace
```

In Xcode:
- Select `Niyah` scheme → real device → run.
- If any target shows "Signing for X requires a development team" — click on the target → Signing & Capabilities → set Team to **Niyah, Inc. (4R55F73KCP)**.
- EAS Build should auto-handle this for cloud builds via the `appleTeamId` in `app.config.js`.

### Verify in Xcode

For each of the 5 extension targets (`monitor`, `report`, `shieldaction`, `shieldconfig`, `widget`):
- **Signing & Capabilities** tab shows:
  - Team: Niyah, Inc.
  - Bundle Identifier matches the App ID
  - Family Controls + App Groups capabilities listed (widget only needs App Groups)
- **Build Settings** shows deployment target matches `expo-target.config.json` (16.0 or 16.1).

### EAS cloud build

`eas build --profile production --platform ios` — should auto-detect all 5 extension targets, request provisioning profiles, sign each. If a target fails: `eas credentials` to inspect.

## When you edit native code

- **Always edit in `targets/<name>/`**, NOT in `ios/<name>/`. The `ios/` dir is regenerated by `npx expo prebuild --clean` and your edits will be lost.
- To open the Xcode-visible "expo:targets" virtual folder: `open ios/Niyah.xcworkspace` → the synchronized group at the top shows the targets.
- After editing Swift, no prebuild needed — Xcode picks up changes automatically via filesystem sync.
- After editing `expo-target.config.json` or any entitlements: `npx expo prebuild --clean` to re-sync.
